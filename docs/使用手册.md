## 1. 通道选择

| 通道 | 安全性 | 推荐度 | 说明 |
|------|--------|--------|------|
| **MQTT** (官方通道) | ✅ 无风险 | ★★★★★ | 走官方控制中心逻辑,不会写坏 EC |
| **EC 直写** (IOCTL) | ⚠️ 有风险 | ★★★ | 绕过控制中心直接操作 EC,用于自定义 |

**优先用 MQTT**。EC 直写仅用于 MQTT 没有的能力(自定义风扇表开关/遥测)。

## 2. MQTT 控制(官方通道,推荐)

### 2.1 连接参数

| 参数 | 值 |
|------|-----|
| Broker | `localhost:13688` |
| 客户端 ID | `PluginClient_1` |
| 用户名 | `PluginClient_User_1`(环境变量 `JL_MQTT_USER`) |
| 密码 | ⚠️ 本机 broker 凭证,不写入文档;运行时经环境变量 `JL_MQTT_PWD` 提供 |
| 控制主题 | `Fan/Control` |
| 状态主题 | `Fan/Status` (读) |

> ⚠️ 客户端 ID 必须是 broker 已创建的账号(`PluginClient_1` 已确认可用;
> 任意 `_N` 后缀不保证存在,`ClientIdentifierNotValid` 会被拒)。

### 2.2 模式切换

发布到 `Fan/Control`:

```json
{"Action":"OPERATING_TURBO_MODE"}    // 狂暴模式 → 0x751=0x10
{"Action":"OPERATING_GAMING_MODE"}   // 游戏模式
{"Action":"OPERATING_OFFICE_MODE"}   // 办公模式
{"Action":"OPERATING_CUSTOM_MODE"}   // 自定义模式 → 0x751=0x80
```

### 2.3 Boost

```json
{"Action":"FAN_BOOST_ON"}            // Boost 开启 → RPM ~5284, 0x751=0x40, 0x768=0x04
{"Action":"FAN_BOOST_OFF"}           // Boost 关闭 → 回 ~3796
```

### 2.4 自定义风扇曲线

```json
{
  "Action": "SET_FAN_SPEED_CURVE_SETTING",
  "Name": "M4T1",
  "Type": "CPU",
  "T0": "30", "T1": "30", "T2": "35", "T3": "40",
  "T4": "45", "T5": "50", "T6": "55", "T7": "60",
  "T8": "65", "T9": "70", "T10": "75", "T11": "80",
  "T12": "85", "T13": "90", "T14": "95", "T15": "100"
}
```

⚠️ 两个坑:
1. **`Type` 必须大写** `"CPU"`/`"GPU"` — 小写 `"cpu"` 会被静默忽略
2. **首点(最低温度)必须 0%** — 否则 EC 拒绝整表(回退内置曲线,风扇不跟随)
3. **先发 `OPERATING_CUSTOM_MODE`,停 ~1.5s,再发曲线** — 顺序反了会被模式切换覆盖

✅ **实测已验证(2026-08-05)**: MQTT 写 `T0:"0",T1-T15:"100"` → 风扇拉满(4739 RPM,88.5%);
首点写 100% → 表被拒(输出不跟随)。单位: 占空比值÷2=百分比(0xC8=200=100%)。

```json
{"Action":"GET_FAN_SPEED_CURVE_SETTING"}    // 读当前曲线
{"Action":"GET_FAN_STATUS"}                 // 读风扇状态(经 Fan/Status 返回)
```

### 2.5 转换灵敏度 (✅ 2026-08-05 逆向, 主题 Fan/Control)

```json
{"Action":"SET_OPERATING_MODE_DETAIL","FanSwitchSpeed":"400"}      // 设灵敏度
{"Action":"SET_OPERATING_MODE_DETAIL","FanSwitchSpeedEnabled":"1"}  // 开关 (0=关)
```

- 范围 **100~12700**(用户提供),当前 400
- 读取: Fan/Status 的 `FAN_FanSwitchSpeed`;控制/开关消息见 2.6d 表格
- 说明: **值越低响应越快**(100≈8s 到目标,400≈20-30s,8000 最慢;实测与"调高=变快"直觉相反)

### 2.6 当前生效曲线 (CPU/GPU 定案, 2026-08-05)

**策略**: 固定基准转速(压得住温度的最安静值)+ 高温爬升,避免频繁变速。

**CPU**(46~80°C): 0,37,37,37,37,37,37,37,54,100
**GPU**(44~78°C): 0,32,32,32,32,32,32,32,50,100

| 温度点 | CPU | GPU |
|--------|-----|-----|
| 46/44°C | 0% | 0% |
| 48/46°C | 37% | 32% |
| 52/50°C | 37% | 32% |
| 56/54°C | 37% | 32% |
| 60/58°C | 37% | 32% |
| 64/62°C | 37% | 32% |
| 68/66°C | 37% | 32% |
| 72/70°C | 37% | 32% |
| 76/74°C | 54% | 50% |
| 80/78°C | 100% | 100% |

- 基准: CPU 37%≈**2350 RPM** / GPU 32%≈**1978 RPM**(实测稳定)
- 温度寄存器: **0x44C=CPU 温度**, **0x44F≈GPU 温度**(官方 System/GpuInfo 校验)
- 官方转速源: MQTT `System/FanInfo`(CpuFanRpm/GpuFanRpm);EC 直读 0x464/465(CPU)、0x46C/46D(GPU,±4%)

### 2.6b RPM-占空比校准表 (实测, 2026-08-05)

**RPM 与占空比非线性**(中段偏高),设目标转速必须查表,不能线性换算:

| 占空比 | CPU RPM | GPU RPM |
|--------|---------|---------|
| 25% | 1617 | 1567 |
| 30% | 1940 | 1863 |
| 32% | 2065 | 1978 |
| 35% | 2243 | 2147 |
| 40% | 2530 | 2400 |
| 45% | 2789 | 2662 |
| 50% | 3062 | 2921 |
| 60% | 3552 | 3252 |
| 70% | 4030 | 3763 |
| 80% | ~3899 | ~3343 |
| 100% | 5284 | 4867 |

**规律**: 25-40% 近似线性(每 5% ≈ 320 RPM);40-70% 斜率变陡;70%+ 趋于饱和。
**测试方法**: 全曲线设同一目标值(首点强制 0),等 30-40 秒完全稳定(EC 平滑滞后大),采样 2 次取一致值;测前把转换灵敏度设 100 可加速(8 秒稳定),测后恢复用户值。
**温度源**: 0x44C=CPU 温度,0x44F≈GPU 温度(控制台显示约低 0~9°C,以 EC 读数为准)。
**常用换算**: 2000 RPM→32% | 2250→35% | 2500→40% | 3000→50% | 4000→70% | 满转→100%(5284)。

### 2.6c 功耗墙 (AMD, ✅ 2026-08-05 实测验证)

**本机是 AMD 平台(Ryzen 9 7845HX)**,控制台界面显示 **SPL / SPPT / FPPT / Tj Max**。
(PL1/PL2/TccOffset 是 Intel 兼容字段,界面不显示;已同步为 AMD 值避免冲突。)

统一消息:`{"Action":"SET_OPERATING_MODE_DETAIL","<字段>":"<值>"}` → Fan/Control

| 控制台名称 | 消息字段 | 状态字段(带CPU_前缀) | 当前值 | 命令 |
|---|---|---|---|---|
| **SPL**(长时功耗) | `CpuAmdSPL` | CPU_AmdSPL | 80 | `spl <值>` |
| **SPPT**(短时功耗) | `CpuAmdSPPT` | CPU_AmdSPPT | 90 | `sppt <值>` |
| **FPPT**(峰值功耗) | `CpuAmdFPPT` | CPU_AmdFPPT | 100 | `fppt <值>` |
| **Tj Max**(温度墙) | `CpuAmdTccTarget` | CPU_AmdTccTarget | 94 | `tjmax <值>` |
| PL1/PL2/TccOffset(Intel) | PL1 / PL2 / CpuTccOffset | CPU_PL1/2/TccOffset | 80/90/94 | `pl1/pl2/tcc` |

> ✅ 实测: PL1 75→76→75、TjMax 96→95→96 均生效。消息字段**无前缀**,状态字段**带 CPU_ 前缀**。
> ⚠️ 功耗墙影响发热/性能,小步改(+/-5)并观察温度(0x44C)。

### 2.7 键盘背光 (✅ 2026-08-05 逆向, 主题 Keyboard/Ctrl)

```json
{"function":"Init"}                                    // 初始化会话(点灯前提!实测必需)
{"function":"SetPower","powerstatus":1}                // 开背光 (0=关)
{"function":"SetLightingLevel","light":"4","mode":"Lighting"}  // 亮度 0-4
{"function":"SetEffectALL","effect":"Breathing","mode":"Lighting","speed":"2"}  // 效果
{"function":"SetPower","powerstatus":0} + {"function":"DeInit"}  // 关 + 清理会话
{"Action":"GETSTATUS"}                                 // 查询状态
```

- **消息格式:控制用 `{"function":...}`,查询用 `{"Action":...}`**
- **必须先 `Init` 再控制**——否则只有状态变化,物理灯不亮(实测);`DeInit` 配对应答,乱序会触发控制台 UI NullReferenceException
- **亮度范围 0~4**(不是 5)
- **单色模式**:`{"function":"SetEffectALL","effect":"Single","mode":"Lighting","MonochromeIndex":"N","speed":"1"}`,N=1~30(1=红, 7=橙, 21=蓝, 均实测;29=黑, 30=白;底层颜色表含 R/G/B + 通道级别)
- **有灯光休眠功能**(当前默认 5 分钟)——灯自动熄灭可能是休眠定时器,不是故障;动作 `KEYBOARD_LIGHTBAR_TIMER_ON` 疑似休眠开关
- **3 种模式**(控制台标签: 单色 / 多彩模式 / 自定义模式):
  - **单色**: `effect:"Single"` + `MonochromeIndex`(N=1~30, 1=红 7=橙 21=蓝 均实测) → ✅ 100%
  - **多彩**: `effect:"<26种>"` + `speed` + `light` + `direction` → ✅ 协议 100%(SingleZone 单区硬件限制,表现同控制台)
  - **自定义**(UserMode 颜色序列): `effect:"UserMode"` + `ManualInterval`(2~10) + `color.ColorBuffer`(6 色限制) → ⚠️ **已知缺口**: 控制台能红蓝交替,外部 MQTT 多次尝试(字符串/数字 51/补字段)均无效,疑似需控制台内部状态配合
- **效果数字映射**(EffecMapping): Single=1 Breathing=2 Wave=3 Reactive=4 Rainbow=5 Ripple=6 Marquee=9 Raindrop=10 Aurora=14 Spark=17 Gaming=21 UserMode=51
- 方向: LeftRight / RightLeft / DownUp / UpDown / OnKeyPressed / Sync
- 控制消息: `Init` → `SetEffectALL`(单色/效果)→ `DeInit`,见上文格式

## 3. EC 直写(自定义控制,有风险)

### 3.1 设备与 IOCTL

| 项 | 值 |
|----|-----|
| 设备路径 | `\\.\ACPIDriver` |
| 读 IOCTL | `0x9C40A488` — 输入 `[addr:4]`,输出 buffer,结果在 `out[0]` |
| 写 IOCTL | `0x9C40A48C` — 输入 `[addr:4][value:4]` |

### 3.2 已验证格式(C# 示例)

```csharp
// 读 EC 寄存器
byte[] ReadEC(IntPtr h, ushort addr) {
    byte[] input = BitConverter.GetBytes((uint)addr);   // 4字节地址, 小端
    byte[] output = new byte[4];
    DeviceIoControl(h, 0x9C40A488, input, 4, output, 4, out _, IntPtr.Zero);
    return output[0];
}

// 写 EC 寄存器
void WriteEC(IntPtr h, ushort addr, byte value) {
    byte[] input = new byte[8];
    Array.Copy(BitConverter.GetBytes((uint)addr), input, 4);  // 前4字节=地址
    input[4] = value;                                          // 后4字节=值
    DeviceIoControl(h, 0x9C40A48C, input, 8, null, 0, out _, IntPtr.Zero);
}
```

### 3.3 安全规则(血泪教训)

1. ❌ **禁止**把 40 字节 `"AeiC"/"ECRR"` 结构**直接当 IOCTL 输入**发给 `0x9C40A48C` —
   驱动会把输入**前 4 字节当 EC 地址**,读到垃圾高地址 → **BSOD 0xA5 的根源**。
   (正确的 ACPI EVAL 结构由驱动内部构建,用户只需传 `{addr}` / `{addr,value}`。)
2. ❌ 禁止猜测格式盲扫 — 每次只测一种已验证格式
3. ✅ **每次写后立即读回**验证
4. ✅ 只写已知地址(见下);不要枚举未知地址
5. ✅ 操作前关闭 MQTT 控制台竞争(避免双方抢写同一寄存器)

### 3.3b ⚠️ 固件写保护边界 (2026-08-05 穷尽测试)

| 区域 | 直接写 | 说明 |
|------|--------|------|
| 0x751 模式 / 0xD8 / 0xD9 | ✅ 可写 | 已验证 |
| **风扇表 0xF2/0xF5/0xF00~0xF5F** | ❌ 固件硬保护 | 24 IOCTL × 各种格式/解锁/标志地址全部被拒 |
| 0x768 Boost 触发 | ❌ | 仅 GCUService/MQTT 可置位 |

**结论:风扇表只能通过 GCUService(MQTT 命令)写入**。直接写 EC 改曲线不可行。

### 3.4 直写示例序列

```text
读遥测:    读 0x464/0x465 → CPU RPM (大端: 0x464<<8 | 0x465)
读模式:    读 0x751 → 0x10=TURBO, 0x40=BOOST, 0x80=USER
切模式:    写 0x751 = 0x10   (切 TURBO)
启用表:    读 0x7C5 → 置 bit7 → 写 0x7C5   (SetEcFanControlRespective 逻辑)
写曲线:    写 0xF2+i (i=0..15) = CPU 占空比曲线 (单位 0.5%, 0xC8=100%)
           写 0xF5+i (i=0..15) = GPU 占空比曲线
           首点(最低温度)强制 0%; 曲线必须单调递增
           温度点固定: CPU=46,48,52,56,60,64,68,72,76,80°C; GPU=44,46,50,54,58,62,66,70,74,78°C(用户提供,以此为准)
应用表:    写 0x7C6 = 0x04
```

> ✅ **实测已验证(2026-08-05)**: 写 0xF2(CPU)/0xF5(GPU) 占空比区 → 转速实时跟随,
> 与控制台 UI 设置 100% 吻合(全 100% → RPM 5272;调低 → 4922)。
> 之前 "曲线不驱动转速" 的结论是错的——原因是 MQTT 把曲线写到了 0xF00/0xF10 错误区域。
